# RPC-398 — Bash/Tool Output Does Not Stream Incrementally in the Rust TUI

**Type:** Bug
**Component:** Tool progress streaming (`codelet/tools`, `codelet/cli`, `codelet/agent-loop`, `codelet/fspec-tui`)

---

## 1. Symptom

In the ratatui `fspec-tui` frontend, when a bash tool (or any tool that emits
incremental progress) runs, its stdout/stderr does **not** appear line-by-line
while the command executes. Instead nothing streams during execution and the
full output appears only when the command finishes, at which point the tool card
immediately collapses to its settled 8-line view.

The TypeScript reference (Ink TUI) streamed a live sliding "tail" window during
execution. The Rust port lost that behaviour.

---

## 2. Architecture (verified)

Active Rust TUI = ratatui `codelet/fspec-tui/` → `codelet-core`/`codelet-sessions`
over the `FspecBackend` trait (embedded in-process tarpc + `broadcast` channels,
RPC-002 §5.1). **`codelet/napi/` is the legacy path and is NOT used by the Rust TUI.**

Both frontends share the same Rust producer machinery for bash streaming:
`codelet/tools/src/bash*.rs` → `tool_progress.rs` registry → `StreamOutput` emitter.

### The downstream pipeline is architecturally complete (all verified ✅)

| Stage | Location | Status |
|---|---|---|
| Line-buffered capture (`read_until(b'\n')`, emits per line) | `codelet/tools/src/bash_streams.rs:65,73,114` | ✅ |
| Emit via registry | `tool_progress.rs::emit_tool_progress` | ✅ |
| Emitter → `StreamEvent::ToolProgress` | `agent-loop/src/background_output.rs:344-356` | ✅ |
| → `StreamChunk::ToolProgress` → broadcast | `background_session.rs` `chunks_tx` | ✅ |
| fspec-tui subscribes `chunks_rx` → `Action::ChunkReceived` | `fspec-tui/src/app/bootstrap.rs:164-179` | ✅ |
| Dispatch `ToolProgress` → fold under ToolCall card | `session_context.rs:107` → `chunk_processor.rs:199 handle_tool_progress` | ✅ |
| Live tail render (`is_streaming` → last-N-line window) | `chunk_wrap.rs collapse_tool_body` | ✅ |

So the rendering side is **not** the problem.

---

## 3. Root Cause — session-id KEY MISMATCH silently no-ops the emit

The tool-progress callback registry (`codelet/tools/src/tool_progress.rs`) is keyed
by `session_id: Uuid` and does an **exact HashMap lookup with no fallback**
(`session_registry.rs:95-100`):

```rust
pub fn with<R>(&self, session_id: &Uuid, f: ...) -> Option<R> {
    self.inner.read().ok().and_then(|g| g.get(session_id).map(f)) // exact match only
}
```

- **Registration key = `Uuid::nil()`** — `codelet/cli/src/interactive/stream_loop.rs:459-462`:

  ```rust
  // BUG-126: Use Uuid::nil() for CLI mode (single-session; no cross-session risk)
  let cli_session_id = Uuid::nil();
  set_tool_progress_callback(cli_session_id, Some(Arc::new(move |chunk, is_stderr| {
      emitter.emit_tool_progress("", "bash", chunk, is_stderr);
  })));
  ```

  Cleared the same way at `stream_loop.rs:1878` (and `gemini_continuation.rs`,
  `recovery_compaction.rs:325`).

- **Emit key = the REAL per-session UUID** — `BashTool` stores `session.id`
  (`bash.rs:66`), built with the real id at `providers/src/claude.rs:536`
  (`BashTool::new(session_id)` where `session_id = session.id`), and emits with it:
  `bash.rs:268` → `spawn_readers(..., self.session_id)` →
  `bash_streams.rs:73` `emit_tool_progress(session_id, ...)`.

`emit_tool_progress(real_id, ...)` looks up the registry under `real_id`, but the
only entry is under `nil` → `get` returns `None` → **the closure is never called →
no `ToolProgress` StreamEvent is ever produced → nothing streams.** The command's
output only appears once it finishes via the separate `ToolResult` path.

There is **no** second registration under the real id anywhere in production code.

### Why Text streams but ToolProgress doesn't

- **Text / Thinking / ToolCall / ToolResult** → emitted synchronously through
  `output.emit()` from within `stream.next()` → broadcast. **Works.**
- **ToolProgress** → emitted asynchronously from a spawned reader task via
  `emit_tool_progress(self.session_id, ...)` → session-keyed registry lookup →
  (registered only under `Uuid::nil()`) → **miss → no-op.**

### Also affects the pure-CLI path

`agent_runner.rs:32` creates `session_id = Uuid::new_v4()` for its `BashTool`, yet
registers the callback under `nil` — the same mismatch exists there.

---

## 4. Key architectural constraint for the fix

`run_agent_stream_internal` (agent-loop) receives `&mut Session`
(`codelet_cli::session::Session`), which has **no `id` field**. The real per-session
UUID is generated by the callers (`agent_runner.rs:32`, `interactive_helpers.rs:636`)
via `Uuid::new_v4()` and passed into `create_rig_agent(session_id, ...)` →
`BashTool::new(session_id)`. The background path builds `BashTool` with
`session.id` (BackgroundSession UUID) but `run_agent_stream_internal` registers the
callback hardcoded under `Uuid::nil()`.

**The fix must thread the real `session_id` down to the registration site so that the
registration key equals the emit key** (the same UUID passed to `create_rig_agent` /
`BashTool::new`). Registration and clearing must both use that id.

---

## 5. Why the bug slipped through testing

Existing streaming tests all use `BashTool::new(Uuid::nil())` with
`call_with_streaming` and an explicit callback — they never exercise the
`Tool::call` → `emit_tool_progress(real_session_id)` → registry-lookup path that the
live fspec-tui uses. **No test covers the registration-key / emit-key agreement for
the real multi-session path.** The regression test for this fix must exercise that
exact path: register under a real UUID, run a `BashTool` built with the same UUID,
and assert that `ToolProgress` chunks are actually received.

---

## 6. Acceptance criteria (draft)

1. When a bash tool runs under a real (non-nil) session UUID, the tool-progress
   callback registered for that session receives each incremental line as it is
   produced.
2. The registration key used by the stream loop equals the emit key used by
   `BashTool` (the `session_id` passed to `create_rig_agent`/`BashTool::new`).
3. Callback registration is cleared using the same session id after the stream ends
   (no leak, no cross-session bleed — preserves BUG-126 session isolation).
4. Incremental `ToolProgress` chunks are delivered while the command is still
   running (not only at completion).
5. A regression test exercises the real end-to-end path: register under a real UUID,
   run a `BashTool` built with the same UUID, assert `ToolProgress` chunks arrive
   before `ToolResult`.
