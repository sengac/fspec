# GitHub Copilot integration comparison

Research date: 2026-10-30. VTCode was cloned to `/tmp/VTCode` at commit `07377ab34da87004ae39080e5640af7cb3676626` (2026-10-26); fspec was inspected at `81ee9f15b8897c235bf54d58d9b2589a60b25e10`, with an existing dirty working tree. VTCode links below are pinned to that commit. This is a source comparison, not a live Copilot compatibility test. Different implementations do not by themselves prove that GitHub has removed or broken fspec's API, or that the CLI is mandatory.

Second-pass verification: 2026-10-30, against the same repository revisions, current official GitHub documentation, pinned official SDK sources, and locally installed `copilot --version` / `--help`. Several first-pass claims were corrected below. No authenticated inference, model-list request, login/logout, or repository-modifying agent session was run.

## Executive summary

fspec integrates directly with the Copilot HTTP service: it runs its own device authorization, exchanges and refreshes tokens, discovers models via HTTP, and routes model completions through rig. VTCode instead integrates with the official `copilot` executable: it delegates login/logout, discovers models via the CLI's headless server, and runs an agent session over JSON-RPC stdio. This is an architectural difference, not just a new endpoint or header. Adopting it would introduce an external runtime and new security, tool ownership, session and migration concerns. The official Copilot SDK also has a Rust implementation and must be evaluated alongside ACP rather than treating VTCode's hybrid adapter as the definitive current protocol. First verify what currently fails with real public and enterprise accounts, and decide whether to retain HTTP, add an SDK/ACP backend, or migrate; do not blindly replace existing functionality.

## Side-by-side findings

### Authentication and deployment

- fspec implements the GitHub OAuth device flow and stores a credential in `~/.fspec/credentials/copilot_auth.json`; it supports GitHub Enterprise domain selection and exchanges the OAuth token for a short-lived Copilot token. See `rust/providers/src/copilot/oauth_device_code.rs`, `oauth_polling.rs`, `auth.rs`, `token_exchange.rs`, `token_refresh.rs`, and `spec/features/github-copilot-oauth-device-flow-token-storage.feature`.
- VTCode explicitly delegates login/logout to the official CLI and optionally probes GitHub CLI authentication. It supports a configured command / `VTCODE_COPILOT_COMMAND` and reports a missing executable: [provider documentation](https://github.com/vinhnx/VTCode/blob/07377ab34da87004ae39080e5640af7cb3676626/docs/providers/copilot.md) and [auth implementation](https://github.com/vinhnx/VTCode/blob/07377ab34da87004ae39080e5640af7cb3676626/crates/codegen/vtcode-llm/src/copilot/auth.rs).
- More precisely, VTCode probes environment credentials (`COPILOT_GITHUB_TOKEN`, `GH_TOKEN`, `GITHUB_TOKEN`), then stored CLI credentials, then optional `gh` authentication (`auth.rs:721`). This is source detection, not an authenticated Copilot entitlement check. Host parsing and non-default-host login arguments exist; enterprise compatibility still needs end-to-end verification. Logout first tries an interactive CLI session, then a direct command fallback (`auth.rs:75`).
- Migration risk: the two credential stores and login UX are not equivalent. Do not assume existing fspec credentials, enterprise hostname configuration, logout semantics, or availability on all supported platforms transfer to the CLI. Verify explicitly.

### Model catalog and routing

- fspec fetches the Copilot `/models` endpoint and consumes model metadata, including limits and reasoning options (`rust/providers/src/copilot/models/`; `spec/features/github-copilot-model-catalog-from-models-endpoint.feature`). `rust/providers/src/copilot/endpoint.rs` selects `/responses` for GPT-5+ except `gpt-5-mini`, and `/chat/completions` otherwise; `completion_model.rs` actually dispatches to the two rig model types. Revalidate this model-name heuristic against current capabilities rather than assuming it is correct.
- VTCode launches a separate `copilot --headless ... --stdio` server and calls `ping` and `models.list`; it filters policy-disabled models and returns IDs/names ([server client](https://github.com/vinhnx/VTCode/blob/07377ab34da87004ae39080e5640af7cb3676626/crates/codegen/vtcode-llm/src/copilot/server_client.rs), [command](https://github.com/vinhnx/VTCode/blob/07377ab34da87004ae39080e5640af7cb3676626/crates/codegen/vtcode-llm/src/copilot/command.rs)). Its model-discovery server uses Content-Length framing; the ACP session transport is separately implemented. Do not assume the two wire formats are interchangeable.
- VTCode's adapter retains only IDs/names, but that does not establish that the CLI protocol lacks richer metadata. fspec retains context/output limits and reasoning tiers; it filters `model_picker_enabled`, not `policy.state` (`rust/providers/src/copilot/models/schema.rs:23`, `builder.rs:29`). The first pass incorrectly implied fspec already handled policy metadata. VTCode filters explicit non-enabled `policy.state` values but accepts missing policy state (`server_client.rs:73`). Define policy handling and metadata provenance explicitly, and validate account-specific model availability.

### Runtime and tools

- fspec's `rust/providers/src/copilot/provider.rs`, `completion_model.rs` and `refreshing_client.rs` run the fspec/rig completion pipeline using bearer tokens, Copilot headers and model-family behavior. Contrary to the first pass, the Copilot DeepSearch branch does **not** build an agent: `rust/agent-loop/src/deep_search_handler.rs:675` returns an explicit “agent builder pending” error after resolving provider configuration. `rust/agent-loop/src/bridges.rs:32` registers this handler, so this is not just obsolete NAPI code; the NAPI copy at `rust/napi/src/deep_search_handler.rs:670` also contains the stub. The provider client accessor exists (`provider.rs:179`), but its existence does not establish a working consumer. Track this existing gap separately from migration regressions, with a real end-to-end acceptance test.
- VTCode starts `copilot --acp --stdio` with configured built-in tool controls, initializes a client, attempts `session.create` and falls back to `session/new`, then sends `session/prompt`. It attempts model selection using `--model` and retries with `COPILOT_MODEL` after any connection/startup error when a model was supplied, not solely an unsupported-flag error ([command](https://github.com/vinhnx/VTCode/blob/07377ab34da87004ae39080e5640af7cb3676626/crates/codegen/vtcode-llm/src/copilot/command.rs#L113), [ACP client](https://github.com/vinhnx/VTCode/blob/07377ab34da87004ae39080e5640af7cb3676626/crates/codegen/vtcode-llm/src/copilot/acp_client.rs#L260)). It attempts custom-tool registration through `session.create` and handles both dot-style and slash-style permission messages. VTCode's internal “v1/v2” and “legacy” naming is not evidence that slash-style ACP is deprecated; official ACP still documents `session/new`.
- Session-creation fallback does **not** itself set prompt-only mode: startup sets `FullTools` after either successful path (`acp_client.rs:342`). Unknown incoming client requests and malformed tool/runtime requests can call `mark_prompt_degraded` (`acp_client.rs:576`, `1082`). Therefore successful fallback must not be taken as proof that custom tool registration or all runtime capabilities survived.
- VTCode flattens system/user/assistant/tool history into text and replaces image/file inputs with omission notices (`providers/copilot.rs:140`, `440`). This is an adapter limitation, not proof that Copilot universally supports only text. Its cached client is keyed by model and tool signature (`providers/copilot.rs:59`). Verify role semantics, image handling, duplicated history, compaction, model/tool changes and resume rather than copying that representation blindly. fspec already has session lineage/replay machinery in `rust/providers/src/copilot/session.rs` and `completion_model.rs`; preserve those invariants when changing the runtime.
- The VTCode runtime mediates tool execution, terminal lifecycle, permission decisions, sandboxing, hooks and budgets; its stream adapter drains queued updates and cancels an active prompt on drop ([runtime ownership notes](https://github.com/vinhnx/VTCode/blob/07377ab34da87004ae39080e5640af7cb3676626/docs/development/copilot-runtime-ownership.md)). Any fspec adapter must preserve fspec's own permission, tool, event, cancellation, persistence and safety boundaries, not allow an unmanaged second agent to bypass them. Investigate session history/resume and sub-agent behavior explicitly; equivalence is not established.
- The CLI subprocess transports bound message sizes, drain/sanitize stderr, manage pending requests and subprocess shutdown ([stdio transport](https://github.com/vinhnx/VTCode/blob/07377ab34da87004ae39080e5640af7cb3676626/crates/codegen/vtcode-llm/src/copilot/transport.rs)). Capture startup failure, timeouts, process exit, malformed/oversized frames, cancellation and cleanup in acceptance tests.

## Proposed work and acceptance coverage

1. Reproduce current fspec behavior with a current Copilot subscription and CLI version; record version, auth type, model IDs, representative errors, endpoint selection, and relevant GitHub documentation. Test public and, where available, enterprise; never record credentials. Distinguish proven breakage from reference-implementation differences.
2. Choose the backend and migration policy, explicitly comparing retained HTTP, official SDK server mode, and standard ACP. If an external runtime is selected, define packaging/bundling versus PATH discovery, version checks, install guidance, login/logout/status, account selection, enterprise support, credential transition and unavailable-runtime behavior. Do not mix ACP and SDK methods or framing based solely on VTCode's fallback logic. If HTTP remains, verify its current support and update model routing, headers, auth and catalog as evidence requires.
3. Specify model discovery, policy filtering, limits/reasoning fallback, streaming, reasoning/tool output, custom tools, explicit permissions, failure reporting, cancellation, process cleanup, session persistence/resume and DeepSearch/sub-agent parity. Avoid silent degraded mode; make unsupported capabilities visible.
4. Write Gherkin scenarios first, then focused fixture-driven integration tests using fake CLI processes or local HTTP servers for happy paths and compatibility/failure boundaries; add opt-in live smoke tests for supported real accounts and platforms. Do not depend on an actual subscription for ordinary CI. Preserve both front doors and existing public/enterprise tests unless an explicit migration decision changes their contract.

## Decisions and unknowns

- Is the CLI required, an optional backend, or just a reference? Which Copilot CLI versions/platforms and enterprise deployments are supported?
- Is fspec's existing direct HTTP API currently broken or unsupported for any specific model/account? What evidence and official policy establish that?
- What happens to current OAuth credentials, persisted sessions, and users without a CLI? Can DeepSearch work without raw completion access?
- What are the intended tool authority, sandbox, MCP and permission policies when the external agent can execute actions? What happens on legacy/degraded sessions?
- VTCode's own runtime documentation states that its adapter unit tests do not exercise a live prompt-session stream-drop/completion race end to end, and a live provider session was outside that refactor's validation. Treat its code as a useful reference, not proof of correctness or a definitive GitHub specification.

## Official-source cross-check and local evidence

### ACP is a distinct supported integration surface

[GitHub ACP documentation](https://docs.github.com/en/copilot/reference/copilot-cli-reference/acp-server), also [pinned documentation source](https://github.com/github/docs/blob/6cbe6413ac7177bb692a78c171a74ae8be50d721/content/copilot/reference/copilot-cli-reference/acp-server.md), documents:

- ACP remains public preview and subject to change.
- `copilot --acp --stdio` uses newline-delimited JSON; stdio is the recommended subprocess integration mode.
- `initialize`, session creation through `session/new`, prompt streaming and client permission handling are the demonstrated path. `session/new` is not described as obsolete.
- Tool availability/exclusion and initial reasoning effort are configured when launching the ACP server, not through `session/new`. Sessions also honor sandbox settings/policy. fspec must test its allowlist and permission boundaries on the actual chosen protocol.
- BYOK is also supported without GitHub login. This is outside the current subscription-focused card unless explicitly added; neither a Copilot subscription nor CLI-managed login is a universal requirement for all runtime configurations.

VTCode tries dot-style `session.create` on its ACP connection before falling back to `session/new`. Its source proves this attempt exists; it does **not** prove a current server accepts that cross-surface method or custom-tool payload. The card must not promote this behavior to an official protocol requirement.

### Official Rust SDK was missing from the original options

Reviewed official SDK revision `e22b95e6ead5e1de7e9a68d3087b8d28dc5f364a` (2026-10-28):

- [Rust README](https://github.com/github/copilot-sdk/blob/e22b95e6ead5e1de7e9a68d3087b8d28dc5f364a/rust/README.md) documents `github_copilot_sdk`, managed runtime lifecycle, session creation/resume, permissions, and `copilot --server --stdio` using Content-Length framing. This is not ACP NDJSON. VTCode's model discovery instead launches `--headless`; test version-specific flag compatibility rather than assuming those flags are interchangeable.
- [Rust manifest](https://github.com/github/copilot-sdk/blob/e22b95e6ead5e1de7e9a68d3087b8d28dc5f364a/rust/Cargo.toml) requires Rust 1.94.0 and defaults to a `bundled-cli` feature at this revision. The repository-wide README says Rust is not bundled by default, so the docs disagree. Pin an actual release and audit its manifest/distribution before deciding packaging or adding a dependency; do not assume users must separately install a CLI. The reviewed main-branch manifest is `0.0.0-dev`, not a recommendation to depend on an unreleased revision.
- [Authentication documentation](https://github.com/github/copilot-sdk/blob/e22b95e6ead5e1de7e9a68d3087b8d28dc5f364a/docs/auth/authenticate.md) supports stored signed-in credentials, app-issued OAuth tokens, environment tokens and BYOK. Existing fspec OAuth-token reuse is therefore a possibility to validate, not something to rule out merely because VTCode delegates login.
- [Generated model capability types](https://github.com/github/copilot-sdk/blob/e22b95e6ead5e1de7e9a68d3087b8d28dc5f364a/rust/src/generated/api_types.rs#L9247) include optional context/output/prompt limits and capability fields; the reviewed section labels its wire surface experimental. This reinforces that VTCode's IDs/names-only adapter is not a complete inventory of runtime metadata. These SDK types do not prove the shape of fspec's HTTP `/models` response; validate each transport independently.

## Verification against the current code (2026-11-01, PROV-163 discovery)

Decision: keep the direct HTTP backend. Verify it and fix only behaviour proven broken; SDK and ACP migration are out of scope.

These findings come from the current tree:
- **DeepSearch is still blocked.** `rust/agent-loop/src/deep_search_handler.rs` returns `"github-copilot DeepSearch agent builder pending: CopilotProvider::client accessor not yet implemented"` for Copilot sessions. The accessor now exists (`CopilotProvider::client()`, `rust/providers/src/copilot/provider.rs:185`), and `auxiliary_agent_builder!`'s default arm (`provider.client().agent(provider.model())`) can build the sub-agent. The branch is stale, so DeepSearch with Copilot fails for every user.
- **Policy is not filtered.** `rust/providers/src/copilot/models/builder.rs:35` filters only on `model_picker_enabled`. `CopilotModelEntry` (`models/schema.rs`) has no `policy` field, so models disabled by organisation policy (`"policy":{"state":"disabled"}`) show in the picker and then fail at request time.
- **No live test exists.** No test exercises a real account. Ordinary CI must not need one, so an opt-in smoke test (`#[ignore]` plus `FSPEC_COPILOT_LIVE=1` and stored fspec Copilot credentials) verifies token exchange, `/models` and one completion. This machine has the `copilot` CLI and `gh`, but no fspec Copilot credentials (`~/.fspec/credentials` holds only `claude_auth.json`), so the live run must be done after a `/login` with GitHub Copilot.
