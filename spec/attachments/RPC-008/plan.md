# RPC-008 — `FspecBackend` trait + transport selector + ratatui app shell

**Parent:** RPC-002
**Predecessor:** RPC-007 (session RPCs + push channels)
**Successor:** RPC-009 (basic frontend: work-units list + REPL)
**Implements:** RPC-002 Slice 01 (foundation: app shell + Compositor) +
parts of Slice 02 (transport plumbing)

## What we want

Create a new `codelet/fspec-tui` crate that hosts the ratatui app shell
defined in `spec/attachments/RPC-002/07-recommended-architecture.md`,
together with a transport-agnostic `FspecBackend` trait and two concrete
implementations (embedded + WebSocket). The app at the end of this card
renders **only a placeholder "Hello" component** plus an ESC-dismiss
dialog; the real list view and REPL arrive in RPC-009. This card is
foundational scaffolding ONLY — it deliberately does not attempt to
solve any UI/UX problem.

The end of this card unblocks the cards that introduce the user-facing
binaries (RPC-010) because all of `App`, `Compositor`, `FspecBackend`,
embedded transport wiring, and WS client wiring exist in a single
testable crate.

## Why this card

We must not write the binary entry points (`fspec`, `fspec daemon`,
`fspec client`) before there is a TUI library to invoke. We must not
hard-code `EmbeddedTransport` into the TUI either, because `fspec
client` will use the WS transport against an already-running daemon.
Hence: a backend trait, a selector, and the app shell — all in one
crate, with no binary entry points yet.

## Existing RPC-005/006/007 artifacts this card builds on

This card creates the FIRST consumer of the dual-transport seam. It must
not re-implement, re-shape, or work-around any RPC-005-era artifact —
both `FspecBackend` implementations are thin adapters over what already
exists.

those decisions are NOT re-opened here. Specifically:

| Q2: roll our own ~30-LoC Compositor (NOT rat-event / rat-salsa) | doc 11 §Q2, RPC-002 description | `compositor.rs` is the homegrown Helix-style implementation per doc 09 §A. NO `rat-*` crate dependency. |

### Starting template

The crate is bootstrapped by copying the upstream
[`ratatui-org/templates/component`](https://github.com/ratatui/templates/tree/main/component)
skeleton (per doc 01 §Headline 1 and doc 03 §D, doc 05 row "ratatui
templates/component"). The template's three structural pieces are
preserved verbatim in spirit (we keep the names so anyone reading the
ratatui template recognises our app):
- `Component` trait with `handle_events` / `update` / `draw`
- `mpsc::UnboundedSender<Action>` action bus
- `tokio::select!` over events / tick / actions / cancel

The Helix-style `Compositor` is the ONE addition we make on top of the
template (~30 LoC), per doc 05 §Helix and doc 07 §3.

### `FspecBackend` trait (transport seam)

```rust
#[async_trait]
pub trait FspecBackend: Send + Sync {
    // RPCs (subset needed to make slice 09 trivially feasible)
    async fn list_work_units(&self) -> Result<Vec<WorkUnitInfo>>;
    async fn list_sessions(&self) -> Result<Vec<SessionInfo>>;
    async fn create_session(&self, role: Option<String>) -> Result<SessionId>;
    async fn send_input(&self, id: SessionId, text: String) -> Result<()>;
    async fn interrupt(&self, id: SessionId) -> Result<()>;

    // Push subscriptions (returns broadcast::Receiver for fan-out)
    fn work_units_rx(&self) -> broadcast::Receiver<Vec<WorkUnitInfo>>;
    fn chunks_rx(&self) -> broadcast::Receiver<(SessionId, StreamChunk)>;
    fn logs_rx(&self) -> broadcast::Receiver<LogRecord>;
}
```

Two implementations:
- `EmbeddedFspecBackend` — wraps `EmbeddedTransport` from `codelet-rpc-embedded`. Constructor takes a `tokio::runtime::Handle` and an `Arc<SharedFspecService>` (preserving RPC-005 Q9 invariant).
- `WebSocketFspecBackend` — wraps `FspecServiceClient` + the
  `work_units_rx`/`chunks_rx`/`logs_rx` exposed by the WS client from
  RPC-006/007. Constructor takes a `Url`.

### App shell

Implements RPC-002 Slice 01 acceptance criteria as written in doc 12
§Slice 01:
- `Priority` enum (`Background = 100`, `Low = 200`, `Medium = 500`,
  `High = 800`, `Critical = 1000`) — verbatim from doc 09 §A.1.
- `EventResult` enum with `Ignored(Option<Callback>)` /
  `Consumed(Option<Callback>)` — doc 09 §A.3.
- `Component` trait with `priority`, `is_active`, `id`, `handle_event`,
  `update`, `render` — doc 09 §A.4.
- `Compositor` (priority sort, FIFO tiebreak via
  `registration_counter`, `is_active` gating, callback-deferred
  mutations, `pop()` / `remove(id)`) — doc 09 §A.5.
- `App` struct + `run()` loop with `tokio::select!` over event stream /
  action receiver / render tick — doc 07 §2.
- `HelloComponent` at `Priority::Background`, centered text via
  `Layout::vertical([Min, Length, Min])` + `Layout::horizontal([Min,
  Length, Min])` (doc 06 §Centered modal helper).
- `HelpDialog` at `Priority::Critical`. Body is a static `Paragraph`
  listing `?` / ESC / `q` only. Triggered by `?`. Wraps `tui_popup::Popup`
  via a small `SizedWidgetRef` adapter (doc 09 §B.3) — the production
  code path is `tui-popup`, NOT a hand-rolled centered rect.
- ESC closes the dialog by returning
  `EventResult::Consumed(Some(Box::new(|c| c.remove(&id))))` — doc 09
  §B.2.
- 12 Compositor unit tests (per doc 09 §A.7 test plan):
  `higher_priority_intercepts_first`, `ignored_consumed_propagates_correctly`,
  `is_active_false_skips_handler`, `fifo_tiebreak_at_equal_priority`,
  `callback_in_consumed_runs_after_event`,
  `modal_pushed_at_critical_intercepts_keystroke`, plus six edge-case
  tests for `pop`, `remove(id)`, empty stack, sort stability under
  re-push, render order bottom-up, action propagation top-down.
- Snapshot test of `HelpDialog` rendering via
  `ratatui::backend::TestBackend` + `insta::assert_yaml_snapshot!` (doc
  06 §Test mapping, doc 07 §8).
- Crossterm init via `ratatui::init()` (alt-screen + raw mode) plus
  `crossterm::execute!(stdout, EnableMouseCapture, EnableBracketedPaste)`.
- Restore via `ratatui::restore()` plus `DisableMouseCapture`,
  `DisableBracketedPaste`. Wired into BOTH `Drop` on the `App`-owned
  terminal guard AND a `std::panic::set_hook` so a panic mid-render
  doesn't leave the terminal in raw mode (doc 07 §2 implies; doc 12
  §Slice 02 lists the panic hook explicitly).

### Mouse + bracketed paste (doc 12 §Slice 02 partial)

This card pulls forward only the parts of doc 12 §Slice 02 that the app
shell needs to be self-consistent on a real terminal:
- `EnableMouseCapture` + `EnableBracketedPaste` on startup, paired
  cleanup on shutdown (incl. panic).
- `Event::Paste(text)` arm in the main loop forwards to a stub
  `Compositor::handle_paste` (just delegates to active layer's
  `handle_event` with a synthetic key sequence in this card — proper
  paste semantics arrive with `tui-textarea` in Slice 06).
- `MouseTrackingToggle` (5-second debounce timer used to allow native
  text selection) is **deferred to the VirtualList card** (RPC-002
  Slice 03/04) — it is meaningless without a list to scroll. Doc 12
  §Slice 02 lists it under "Wire up the foundation"; we move it because
  no consumer in this card or RPC-009 needs it.

### Theme

Minimal `Theme` struct (doc 07 §6): `fg`, `bg`, `border`,
`border_focused`, `selection_bg`, `selection_fg`, `dim`, `error`,
`warning`, `success`. One implementation: `Theme::default()` (dark).
Stored as `Arc<Theme>` on `App` and passed by reference to render calls.
A `light()` variant is NOT in scope — RPC-002 doc 12 lists "Theme system
(light + dark)" as its own cross-cutting work unit.

### `App::new()` signature

```rust
impl App {
    pub fn new(backend: Arc<dyn FspecBackend>) -> Self;
    pub async fn run(self) -> Result<()>;
}
```

The backend is supplied externally — the TUI crate has no idea whether
it is embedded or remote.

8 points. The Compositor and trait are small. Crossterm init/teardown
across platforms + the panic hook + the WS client adapter (since
RPC-007 only handed us the raw broadcast channels) are the three
non-trivial pieces.
