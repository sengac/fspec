# WT-010 — `restore_ghost_commit` ignores its `force` parameter (and never updates the worktree index)

## Problem

`rust/git/src/ghost_commit.rs:444-449`:

```rust
pub fn restore_ghost_commit(
    dir: &Path,
    work_unit_id: &str,
    checkpoint_name: &str,
    _force: bool,          // ← parameter accepted, underscore-prefixed, never read
) -> Result<RestoreResult> {
```

The body unconditionally overwrites every checkpoint file (`fs::write`, `:487`) and
deletes every file added after the checkpoint (`fs::remove_file`, `:496`) — with **no
conflict detection at all**, regardless of `force`.

The documented contract promises otherwise:

- doc comment `:434`: *"force - If true, overwrite without conflict detection"*
  (implying force=false detects conflicts),
- NAPI binding `rust/napi/src/git.rs:324-338`: `force: Option<bool>` passed straight
  through (`force.unwrap_or(false)`),
- the fspec checkpoint UX (TUI checkpoint restore / `fspec-core restore-checkpoint`
  commands) inherits that expectation.

So `force=false` (the default) silently destroys local modifications made after the
checkpoint — exactly the data-loss scenario the parameter exists to prevent.

### Secondary defect in the same function

Restore writes files to the working directory only. It **never updates the worktree's
git index** (`<repo>/.git/worktrees/<sid>/index`). After a restore:

- the index still reflects the pre-restore state → `git status` inside the worktree
  reports the restored files as modified/deleted (the index-vs-workdir divergence),
- and because `collect_worktree_files` (tree_utils.rs) keys tracked-file reads on index
  entries, the *next* checkpoint taken immediately after a restore will compute its
  `changed_files` against a stale index baseline.

Compare: `restore_ghost_commit_file` (RPC-362, `:524`) has the same index gap.

## Impact

- Data loss: restore overwrites uncommitted work with zero warning when `force` is
  absent/false (the default path from the NAPI binding and from
  `BackgroundSession::restore_checkpoint` → `restore_ghost_commit(worktree, id, label,
  true)` — note the session checkpoint path actually passes `true`, so within-session
  checkpoints always clobber; only the externally-facing NAPI/CLI path is
  force-honoring-in-name-only).
- Confusing post-restore `git status` in worktrees (index/workdir skew).

## Proposed fix

1. Implement the documented behavior: when `force == false`, run a
   diff-before-write (checkpoint tree vs current workdir, the machinery of
   `get_checkpoint_diff_files` at `:720` already exists) and return a
   `GitError::ConflictError { files }` (or a new `RestoreConflict`) instead of
   overwriting; `force == true` keeps today's semantics.
2. After restoring files, rebuild the worktree index from the restored tree
   (reuse `initialize_worktree_index` from `worktree.rs:249`, or a
   `repo.index_from_tree(tree_of_checkpoint)` + write) so index and workdir agree.
3. Update the feature/spec docstring for checkpoint restore
   (`spec/features/checkpoint-restore-shows-confusing-merge-terminology-when-it-actually-overwrites-files.feature`
   exists as a UX complaint already — link this card to it) and add tests:
   - modified-after-checkpoint file + `force=false` → error, file untouched;
   - `force=true` → overwrite;
   - post-restore index == workdir (git status clean-ish).
