# WT-004 — Worktree path-isolation (TOOL-014 / GIT-020) is dead in the `fspec` binary

## Problem

The entire tool-layer path-isolation mechanism — the thing that pins an isolated session
to its git worktree — is gated behind a **global OnceLock callback that is only ever
registered by the NAPI adapter**. The `fspec` binary (combined/daemon mode, the primary
Rust frontend) never registers it, so in that binary:

- `get_isolation_context(session_id)` → always `None`
- `validate_and_resolve_path_with_isolation(path, None, tool)` → **"No isolation context
  — allow all paths"** (the documented fall-through)
- `BashTool` / `UnifiedExec` `resolve_cwd` → no worktree override → process cwd

i.e. an isolated session in the Rust TUI can read/write the main project root, `/tmp`,
anything — the worktree is a cosmetic badge, not a boundary.

## The callback chain (and where it breaks)

**Storage** — `rust/tools/src/facade/wrapper.rs:637`:

```rust
static GET_EFFECTIVE_CWD_CALLBACK: std::sync::OnceLock<GetEffectiveCwdCallback> =
    std::sync::OnceLock::new();

pub fn set_get_effective_cwd_callback(callback: GetEffectiveCwdCallback) { ... }
pub fn get_isolation_context(session_id: Uuid) -> Option<IsolationContext> {
    GET_EFFECTIVE_CWD_CALLBACK.get().and_then(|cb| cb(session_id.to_string()))
}
```

**The only production registration** — `rust/napi/src/bridges.rs:179-188`:

```rust
pub(crate) fn init_block_notification_callbacks() {
    set_block_notification_callback(emit_block_notification_to_tui);
    set_get_work_unit_stage_callback(get_session_work_unit_stage);
    set_get_effective_cwd_callback(get_session_effective_cwd);   // ← GIT-020
}
```

called from `session_set_global_chunk_callback` (`rust/napi/src/session_bindings.rs:1473`)
— an NAPI export, only reachable from the Node/TS host.

**Registration in the `fspec` binary** — `build_service` (`rust/fspec/src/common.rs:86-157`):
initializes the data dir, blocklist, watcher, SessionManager + `FspecAgentHooks`.
`set_get_effective_cwd_callback` appears **nowhere** in the binary's dependency tree:

```
grep set_get_effective_cwd_callback rust/  →
  tools/src/facade/wrapper.rs   (definition)
  tools/src/facade/mod.rs       (re-export)
  napi/src/bridges.rs           (the ONLY caller)
```

The napi implementation it would need (`get_session_effective_cwd`,
`rust/napi/src/bridges.rs:349`) is itself a ~25-line function over
`SessionManager::instance()` — trivially relocatable to a NAPI-free crate.

## Blast radius (all per-session tools)

Every tool facade wrapper calls `validate_and_resolve_path(session_id, …)` on file args:
`Read/Write/Edit` (`FileToolFacadeWrapper`), `Grep/Glob/AstGrep/AstGrepRefactor/Ls`
(search wrappers), and the Bash path: `rust/tools/src/bash.rs:67`
`get_effective_cwd` and `rust/tools/src/unified_exec/tool.rs:67`
(Session isolation takes precedence over `args.cwd`). With the callback unregistered,
all of these degrade to "no isolation":

| Tool | What isolation SHOULD do (TOOL-014 feature) | What it does in the binary |
| --- | --- | --- |
| Read/Edit/Write | resolve relative paths inside worktree; reject absolute paths into the project root | allow any path |
| Grep/Glob/AstGrep | search only the worktree | search anywhere |
| Ls | list the worktree | list anywhere |
| Bash | run in worktree cwd | run in process cwd |

The spec for this behavior is `spec/features/require-session-id-for-all-tools-to-support-worktree-isolation.feature`
(its tests only exercise the pure `validate_and_resolve_path_with_cwd` helper, so they stay
green while the wiring is dead — a classic "tested the function, not the system" gap).

## Secondary consequence: the *blocklist* and *work-unit-stage* callbacks have the same shape

`BLOCK_NOTIFICATION_CALLBACK` and `GET_WORK_UNIT_STAGE_CALLBACK` are registered in the
same `init_block_notification_callbacks` — they are equally dead in the binary. (Worth a
separate card if stage-gated writes or block-notification UX are relied on in the Rust TUI;
the blocklist enforcement itself was fixed independently by RPC-407's
`codelet_tools::blocklist::init_blocklist` call in `build_service`.)

## Proposed fix

1. Move `get_session_effective_cwd` (rename: `session_isolation_context`) into a NAPI-free
   crate that has access to `SessionManager` — `codelet-sessions` is the natural home
   (`SessionManager::instance()` + `BackgroundSession.worktree_path` / `.project`).
2. In `build_service` (`rust/fspec/src/common.rs`), after constructing the manager:
   ```rust
   codelet_tools::set_get_effective_cwd_callback(codelet_sessions::session_isolation_context);
   ```
   (or extend the hooks install step — `manager.set_hooks` — with a callback registration
   hook so every front door wires identically, per the "two front doors, one source of
   truth" rule.)
3. Do the same for block-notification + work-unit-stage callbacks (or at least log a
   warning at startup when they remain unregistered in a combined-mode build).
4. Add an integration test (temp dir + real git repo, mirroring
   `rust/tools/tests/*_session_isolation_test.rs`): register the callback via the
   session-manager path, create an isolated session, assert a `Write` to the project root
   fails with "outside isolated worktree" and a write into the worktree succeeds.
