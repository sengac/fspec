# BUG-241: Codex metadata and safety-buffering behavior

## Summary

Codex sessions sometimes display routine transport metadata as meaningful status
changes, for example:

```text
Codex buffering inactive

I’ll review the staged changes, then create a conventional commit.

Codex buffering inactive; moderation status received
```

These strings are generated by fspec, not assistant output or upstream error
messages. They do not establish that safety buffering actually started or stopped,
or that the user's request was flagged or rejected.

The defect is broader than wording: fspec conflates diagnostic snapshots with
user-facing events, diverges from upstream buffering parsing, and lacks equivalent
turn-scoped waiting presentation. Fix the protocol and lifecycle boundaries rather
than filtering these two strings from rendered output.

## Impact

- Normal requests acquire misleading buffering notices, including an inactive
  notice when no active buffering notification ever occurred.
- Moderation presence is exposed as a user notification even though upstream's
  terminal UI intentionally ignores that metadata notification.
- Later metadata changes can repeat stale moderation or verification labels.
- Malformed or unrelated metadata can activate fspec's buffering flag.
- Faster-model advice can remain stale or resolve differently from upstream.
- Existing tests and specifications protect some divergent behavior, so passing
  them alone does not demonstrate upstream compatibility.

There is no evidence here that requests fail, buffering is performed locally,
moderation rejects requests, or sensitive raw moderation payloads are exposed.

## Current fspec data flow

1. HTTP and WebSocket transport paths supply the session-owned metadata handle.
2. `rust/providers/src/codex/streaming.rs:129` applies each parsed event to it
   before ordinary response-event handling.
3. `rust/providers/src/codex/metadata.rs:95` compares the entire status snapshot.
   Any changed field invokes the observer, not just user-relevant transitions.
4. `rust/providers/src/codex/session.rs:186` formats every changed snapshot as a
   notification string.
5. `rust/sessions/src/provider_status.rs:13` forwards that string through
   `StreamChunk::UserNotification` with informational severity.
6. `rust/fspec-tui/src/store/agent_view/record_chunk.rs:116` appends a displayed
   notification chunk; this is not an updateable buffering waiting indicator.

The status includes request/model identifiers, reasoning-header presence, rate
limits, buffering, faster-model advice, verification, and moderation presence.
`notification()` always begins with the current boolean buffering state, even
when the changed field is not included in the resulting text.

## Findings and upstream comparison

### 1. Snapshot changes become invented buffering transitions

Fspec: `rust/providers/src/codex/metadata.rs:30` and `:95`.

Buffering defaults to false. A reasoning-header or rate-limit update can change
the snapshot and emit `Codex buffering inactive` without any buffering event.
Distinct snapshots can also format to identical notification strings.

Upstream handles typed events separately in
`codex-rs/core/src/session/turn.rs:3014`. Server-model, verification, moderation,
buffering, reasoning accounting, and rate-limit events have different consumers.
Ordinary metadata changes do not synthesize a buffering notification.

Required correction: retain diagnostic/accounting updates without automatically
announcing the entire snapshot to users. Do not infer a transition from the
default value of a field unrelated to the event.

### 2. Moderation presence is noisy and sticky

Fspec: `rust/providers/src/codex/metadata.rs:209` sets `moderation_received` true
for non-null metadata and never clears it. The formatter adds the moderation
suffix whenever any subsequent snapshot is notified. Turn start and reset only
reset other subsystems: `rust/providers/src/codex/session.rs:163`.

Upstream extracts moderation metadata only from `response.metadata` events:
`codex-rs/codex-api/src/sse/responses.rs:232`. Its TUI explicitly ignores
`TurnModerationMetadata`: `codex-rs/tui/src/chatwidget/protocol.rs:389`.

Required correction: keep moderation presence diagnostic-only and define explicit
request/turn versus session lifetimes. Do not replay old moderation or verification
labels through unrelated updates. Preserve actionable verification presentation;
upstream deduplicates verification within a turn, rather than discarding it.

### 3. Buffering parsing does not match the wire contract

Fspec: `rust/providers/src/codex/metadata.rs:189`.
Upstream: `codex-rs/codex-api/src/sse/responses.rs:244` and
`codex-rs/codex-api/src/common.rs:134`.

Upstream behavior:

- Prefer a present top-level `safety_buffering` value over nested metadata.
- Fall back to nested `metadata` only when the top-level field is absent, the
  enclosing event type is `response.metadata`, and `metadata.type` is
  `safety_buffering`.
- Deserialize a valid object containing string arrays `use_cases` and `reasons`,
  and an optional `retry_model`. Ignore invalid payloads.
- Boolean values, including `false`, are not start/stop instructions. They produce
  no buffering event. Explicit null also suppresses nested fallback.

Fspec instead treats booleans as state changes, treats every object as active,
and activates from nested `metadata.type` without checking the outer event type.
A malformed top-level object, or explicit null combined with nested metadata,
can therefore yield a different result from upstream.

Upstream regression anchors:
`codex-rs/codex-api/src/sse/responses.rs:1750`, `:1878`, `:1921`, and `:1939`.
These cover boolean handling, precedence, event-type gating, and malformed data.

### 4. Faster-model advice has incorrect lifetime and precedence

Fspec updates `faster_model` from headers and from top-level object string values
only: `rust/providers/src/codex/metadata.rs:145` and `:197`.
It does not process a nested buffering object's `retry_model` equivalently.
Explicit null leaves old advice in place; an omitted value retains the previous
event's advice instead of resolving from the current transport header treatment.

Upstream resolves advice for each valid buffering event:

| Wire value | Expected faster-model suggestion |
| --- | --- |
| `retry_model` omitted | Current response/header treatment fallback |
| `retry_model: null` | None, even when a header fallback exists |
| `retry_model: "model-name"` | That event's model name |

References: `codex-rs/codex-api/src/sse/responses.rs:259` and `:1812`;
`codex-rs/codex-api/src/safety_buffering.rs:8`;
`codex-rs/codex-api/src/endpoint/responses_websocket.rs:987`.

Keep HTTP and WebSocket semantics consistent. A faster-model suggestion must not
silently change the selected model or automatically retry a user's request.

### 5. Buffering presentation is not tied to the active waiting turn

Upstream: `codex-rs/tui/src/chatwidget/safety_buffering.rs:49`, `:61`, and `:104`.

Codex scopes buffering UI to the active turn, rejects stale/replayed updates,
deduplicates its prompt, and dismisses it when an assistant message starts.
It presents a temporary waiting explanation, with an optional user-controlled
faster-model retry, rather than appending active/inactive transcript messages.
Turn completion and interruption also clear waiting state.

Fspec has a stream-drop guard that clears its boolean, but that is not equivalent
to upstream's presentation lifecycle. The guard's update can itself generate an
inactive notification. Separate protocol observations from UI waiting state and
local cleanup; cleanup must not imply a server-originated buffering transition.

## Existing requirements that must be revisited

The mismatch was partly deliberate in PROV-153, not merely an untested accident:

- `spec/features/codex-metadata-safety-status.feature` explicitly says false clears
  status even though the pinned upstream parser ignores it. Its buffering and
  moderation scenarios encode the divergent policy.
- `spec/features/codex-session-metadata-status.feature` routes sanitized status
  changes through existing user notifications.
- `spec/attachments/PROV-153/design-api.md` documents boolean start/stop behavior,
  full-snapshot notification formatting, and visible moderation presence.
- `rust/providers/tests/prov153_codex_metadata.rs:140` requires false to clear
  buffering. Its moderation test also requires a rendered moderation notice.
- `rust/agent-loop/tests/prov153_codex_session_status.rs:88` requires active and
  inactive notifications, protecting the noisy behavior.

Update acceptance criteria before tests and implementation. Preserve the old
attachment as historical context, with a supersession note if appropriate; do
not silently rewrite the audit history. Maintain scenario/test/implementation
traceability and update affected coverage mappings when scenarios change.

## Acceptance and regression-test plan

Develop scenarios first, then demonstrate meaningful RED tests against current
behavior. Keep each generated scenario mapped to its corresponding test.

| Case | Expected result |
| --- | --- |
| Headers or rate limits change; no buffering payload | Diagnostics update; no buffering notification |
| Moderation metadata arrives, then unrelated updates | No user-visible moderation receipt messages |
| Valid top-level buffering object | Recognized buffering event; private reasons stay private |
| Valid nested object on `response.metadata` | Same semantics as valid top-level data |
| Nested object on a different event type | No buffering event |
| Boolean true or false; explicit null; malformed object | Ignore as buffering events; honor top-level presence precedence |
| Nested fallback plus present invalid top-level value | No fallback activation |
| Retry model omitted, null, or string across successive events | Resolve each event using upstream precedence, without stale advice |
| Active buffering followed by assistant output | Waiting presentation disappears without an inactive transcript notice |
| Duplicate, stale-turn, or replayed buffering updates | No duplicate prompt or resurrection of old waiting UI |
| Completion, failure, cancellation, reset, or new turn | Transient waiting state clears; unrelated diagnostics remain valid |
| Recognized verification recommendation | Appropriate deduplicated actionable notice, not a snapshot suffix |
| Ordinary non-Codex provider | No Codex metadata presentation |
| HTTP versus WebSocket delivery | Equivalent parsing, advice resolution, and presentation behavior |

Use synthetic local streams, real session paths, and shared test helpers rather
than live credentials or provider traffic. Assert notification absence as well as
presence. Preserve text/tool ordering, exactly-once usage delivery, cancellation,
private routing state, and existing recovery notifications.

## Scope, implementation guidance, and verification

- Separate diagnostic snapshot observation from semantically typed presentation
  events. Avoid string-based suppression at the final renderer.
- Keep raw moderation data, buffering reasons, credentials, and routing values
  out of notifications and default diagnostic logs.
- Retain transient cleanup on stream drop; do not conflate a physical request's
  end with the entire logical turn's waiting lifecycle.
- Explicitly define request/turn/session field ownership and reset behavior.
- Inspect existing UI/status channels before selecting a presentation mechanism.
  Ask before a major refactor or shared protocol redesign. Full upstream menu
  parity is not required to eliminate these misleading notices.
- Do not change provider authentication, routing, token accounting, continuation,
  selected model, or transport retry policy to solve this presentation bug.
- Run targeted provider and session integration tests using `ci-test` and bounded
  concurrency; include the updated PROV-153 targets and new BUG-241 regressions.
- Run scoped Cargo check, Clippy, formatting, feature/tag validation, and coverage
  audits. Never run unscoped workspace tests. Record pre-existing unrelated
  failures honestly rather than broadening this card to fix them.
