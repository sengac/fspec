# WT-008 — `/merge-worktree`: "FastForward" strategy is ignored, nothing is committed, and `merge_commit` can never be populated

## Problem

The TUI merge flow sends a strategy that the backend explicitly discards, and the result
type advertises a commit SHA that can never be produced:

### 1. `MergeStrategy` is wire-dead

`rust/fspec-tui/src/app/dispatch_merge_worktree.rs:125-127`:

```rust
match backend
    .merge_session_worktree(sid_for_task.clone(), MergeStrategy::FastForward)
    .await
```

`rust/sessions/src/handle_impl.rs:1934-1941`:

```rust
fn merge_session_worktree(&self, session_id: &SessionId, strategy: MergeStrategy)
    -> Result<MergeOutcome, String> {
    // The strategy is reserved for future evolution — the codelet-git
    // layer currently has only one merge algorithm.
    let _ = strategy;
```

There is exactly one algorithm (`merge_session` → `apply_session_changes`, a
working-tree copy with a byte-level three-way merge — see
`spec/features/rpc057-merge-worktree-dispatch.feature` architecture notes and
`session_status.rs:504`). The enum
(`codelet_rpc_types::MergeStrategy`) exists to promise a second strategy that does not
exist; any client that sends a different value gets FastForward behavior with no error.

### 2. Nothing is committed

`apply_session_changes` copies files into the main working tree and deletes files
(`session_result.rs:311-341`); it never touches the main repo's index or HEAD.
`merge_session` (`session_status.rs:504-525`) then just removes the session manifest.
So after a "successful merge":

- main's **index and HEAD are untouched** — all merged changes are uncommitted in the
  user's working tree, mixed with whatever the user had there.
- `MergeOutcome.merge_commit` is hard-coded `None`
  (`handle_impl.rs:1956-1958`: *"codelet_git::merge_session does not surface the
  resulting commit SHA today"*), so the TUI success notice
  (`dispatch_merge_worktree.rs:210-218`) can never render the `(commit)` suffix it
  formats for.
- The slash-command description ("Merge worktree changes and close session",
  `slash_commands.rs:159`) and the dialog copy both imply a git merge; what actually
  happens is a directory copy.

### 3. `NoChanges` detection is diff-based, not commit-based

`MergeStatus::NoChanges` is derived from
`total_changed == 0` over the *working-tree* diff lists
(`handle_impl.rs:1945-1952`). Because the worktree diff ignores gitignored files
(WT-006), a worktree whose only delta is ignored content reports NoChanges — the dialog
is skipped entirely and the user gets a one-line notice with no record that a worktree
existed.

## Impact

- Users expect a commit; get an uncommitted working tree (surprising, and dangerous if
  the user then does their own `git commit -a` with unrelated files staged).
- The strategy enum is a trap for future clients — "rebase" would silently behave as
  "copy".
- `merge_commit` is dead wire surface.

## Proposed fix

Options (pick one, document in the feature file):

1. **Honest copy (minimal):** rename strategy variants, document that merging is a
   working-tree copy, remove `MergeStrategy` from the wire or make non-FastForward
   values return an explicit `Err(UnsupportedStrategy)`. Keep `merge_commit: None`.
2. **Real merge (recommended, larger):** after the copy succeeds, in `merge_session`:
   `git_add .` + `git_commit` in the MAIN repo (the `codelet_git::repo_ops` helpers
   exist but must be made worktree-aware — WT-006(d)), return the new SHA in
   `MergeResult`; surface it through `MergeOutcome.merge_commit` so the TUI notice shows
   it. Respect `strategy`: FastForward = only when main HEAD == base (else fall back to
   a merge commit or error), giving the field actual meaning.
3. At minimum, make `inspect_session_changes`/the dialog report ignored-content deltas
   so `NoChanges` is honest (pairs with WT-006).
