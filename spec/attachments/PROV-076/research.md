# PROV-076 — Custom-provider slash commands and scaffolding UX

## Problem

Creating / deleting / editing a custom Rhai provider today requires users to:

1. Manually `mkdir -p ~/.fspec/providers/`
2. Hand-write a JSON schema (no template)
3. Hand-write a `.rhai` script (no stubs for the 7 lifecycle functions)
4. Restart the TUI or hope for auto-discovery (no signal available)

There is exactly one CLI-adjacent path, `initProvider(projectRoot, name, template)` NAPI (`session_manager.rs:8276`), which writes a single `<name>.json` to project-local `.fspec/providers/` only. No global support. No Rhai script scaffolding. Not exposed via any TUI command.

## Target: structured `/provider` sub-commands

The current `/provider` handler (`AgentView.tsx:2673-2675`) opens the settings screen with no sub-argument parsing. Extend to accept:

```
/provider                        -> open settings screen (current behavior)
/provider list                   -> list all providers (built-in + custom) inline
/provider init <name>            -> open init wizard (interactive)
/provider init <name> --template=openai-compatible --scope=global
/provider test <name>            -> run testProvider() inline, show result
/provider validate <name>        -> run validateProvider() inline
/provider delete <name>          -> confirm then deleteProvider(name)
/provider edit <name>            -> open file (config) in $EDITOR
/provider reload                 -> rediscoverProviders() + invalidateRegistry()
/provider paths                  -> print fspecPaths() for user orientation
```

Slash command parser lives at `src/tui/utils/slashCommands.ts:26`. Current entry:

```ts
{ name: 'provider', description: 'Configure API providers', requiresSession: false }
```

Extend `SLASH_COMMANDS` with sub-command completion metadata. Completion UX:

- `/provider <tab>` → suggest `list init test validate delete edit reload paths`
- `/provider init <tab>` → suggest existing / all known custom templates
- `/provider test <tab>` → autocomplete with current provider slugs from Rust registry

## Init wizard

Invoked by `/provider init <name>` (or `/provider init` then prompt for name). Wizard steps:

1. **Validate slug** — call `isProviderNameAvailable` (PROV-072). Show conflict error inline if taken.
2. **Choose scope** — `global` (`~/.fspec/providers/`) or `project` (`<cwd>/.fspec/providers/`). Default: global.
3. **Choose template**:
   - `openai-compatible` — OpenAI-style REST, no Rhai script (fastest for vLLM / Ollama / OpenRouter-compatibles).
   - `anthropic-compatible` — Anthropic messages API facade.
   - `rhai-full` — No facade; scaffolds a `<name>.rhai` with stubs for all 7 required lifecycle functions.
4. **Configure base URL / env var name** — template-specific form.
5. **Declare at least one model** — alias + id + optional context_window / max_output_tokens.
6. **Write files** — call `initProvider(scope, name, template)` NAPI (PROV-072 extension).
7. **Invalidate registry + reload** — `invalidateProviderRegistry()` then navigate to `/provider` screen focused on the new entry.

Each step is a `HookMode` variant on `useProviderSettingsState`:

```ts
| { type: 'init-wizard-slug'; input: string }
| { type: 'init-wizard-scope'; name: string }
| { type: 'init-wizard-template'; name: string; scope: string }
| { type: 'init-wizard-config'; name: string; scope: string; template: string; fields: Record<string, string> }
| { type: 'init-wizard-models'; /* ... */ }
| { type: 'init-wizard-confirm'; /* final preview */ }
```

Cancel at any step returns to the list view without writing files.

## Rhai script template for `rhai-full`

The scaffold must include stubs for the 7 required lifecycle functions documented in PROV-062. Research shows the required signatures are auto-checked at load time by `ScriptLoader` (`codelet/providers/src/custom/script_loader.rs`). The wizard must generate:

```rhai
//! Custom provider: <name>
//! Generated by `fspec /provider init <name>` — edit to taste.
//! Lifecycle contract defined in spec/features/provider-config-loader-and-rhai-script-compiler.feature

// 1. Build HTTP request for a chat completion.
fn build_request(state, messages, tools, options) {
    // ... return a #{ url, method, headers, body } map
    throw "build_request not implemented for <name>";
}

// 2. Parse a non-streaming HTTP response into the canonical assistant message.
fn parse_response(state, response) {
    throw "parse_response not implemented for <name>";
}

// 3. Parse a single SSE chunk into 0+ stream events.
fn parse_stream_chunk(state, chunk) {
    throw "parse_stream_chunk not implemented for <name>";
}

// 4. Render the system prompt string to send over the wire.
fn render_system_prompt(state, system_prompt) {
    return system_prompt;
}

// 5. Map an `InternalTool` call to provider-native shape.
fn map_tool_call(state, tool_call) {
    return tool_call;
}

// 6. Inverse of map_tool_call — provider-native shape -> InternalTool.
fn unmap_tool_call(state, raw) {
    return raw;
}

// 7. Refresh credentials (no-op for static API keys).
fn refresh_credentials(state) {
    return state;
}
```

When `facade` is set, only `render_system_prompt`, `map_tool_call`, `map_tool_params` (optional), and `refresh_credentials` are meaningful overrides — the template should comment out the others.

## Edit flow

`/provider edit <name>` opens the config JSON (or script) in `$EDITOR`. Implementation path:

1. Resolve `configPath` / `scriptPath` via `showProvider(name)` (PROV-072).
2. Present a choice between config / script when both exist.
3. Spawn `$EDITOR "$path"` via the shared exec facade (reuse bash tool wrapping).
4. On editor exit, run `validateProvider(name)` (PROV-072) and display any errors.
5. Call `rediscoverProviders()` + `invalidateProviderRegistry()` so the settings view picks up changes.

Fallback when `$EDITOR` is unset: open a scrolling read-only preview (same `custom-provider-script-view` mode from PROV-074) and hint the user to set `$EDITOR`.

## Validation & error surfacing

`init` wizard + `edit` flow both call `validateProvider()` before completing. Errors should render with:

- Filename + line/column when JSON parse fails.
- Missing required lifecycle function names when Rhai compile fails.
- Hint: `fix with:  /provider edit <name>`

## Backwards compatibility

`/provider` with no arguments still opens the settings screen (existing behavior). All sub-commands are additive.

## Test plan

- Unit: slash-command parser extracts sub-command + positional args + flags.
- Wizard: each step renders and advances/rewinds; cancel at any point leaves no files behind.
- `/provider init --scope=global` writes under `FSPEC_HOME` (test fixture).
- `/provider delete` confirms then removes both JSON and `.rhai` from disk, invalidates registry.
- `/provider reload` after an external file mutation updates the next `/provider` list.
- `/provider edit` spawns `$EDITOR` with correct path, re-validates on exit.

## Acceptance summary

- `/provider list|init|test|validate|delete|edit|reload|paths` all function end-to-end.
- Init wizard scaffolds correct JSON + optional Rhai script.
- `rhai-full` template compiles against `ScriptLoader` (stubs throw, but required function set is satisfied).
- All mutations invalidate the Rust-backed TS registry cache.
- Slash-command autocomplete knows about sub-commands and custom-provider slugs.
