# Agent input delivery and interruption research

Research date: 2026-10-30. fspec examined at `81ee9f15b8897c235bf54d58d9b2589a60b25e10` **plus uncommitted working-tree changes**; some admission work is actively in progress. VTCode inspected locally at `07377ab34da87004ae39080e5640af7cb3676626`; OpenCode upstream at `237a847056522ec78a5c64ab7db5a19736e1ea58`. These are source observations, not claims of live runtime testing.

## Executive summary

The likely missing term is **steer**. OpenCode distinguishes (1) interrupt the active execution, (2) steer the ongoing interaction at a safe model/tool boundary, and (3) queue a separate follow-up turn. VTCode also has queue and external steering, though its built-in TUI defaults differ. These words are not universal: the request describes queue as the **LLM polling** for input, which is a fourth *delivery mechanism*, not automatically the same thing as OpenCode's next-turn queue. Confirm the desired semantics rather than silently substituting one for another.

Recommended design: an explicit per-submission mode and durable per-session inbox, with the loop owning all history changes. Deliver steering automatically at safe boundaries, and process queued follow-ups after the current turn finishes. Keep interrupt as a separate explicit control; if interrupt-and-submit is desired, make its cancellation and ordering policy explicit. If actual model-invoked polling is required, add a provider-independent poll tool over the same inbox, with clearly specified fallback and liveness; do not rely on the model choosing to poll for guaranteed delivery. Do not claim an in-flight model generation can read a new message without terminating and restarting its request.

## Proposed implementation scope

1. Specify a mode matrix: idle/busy, streaming, concurrent tool batch, between steps, turn completion, compaction, cancellation, shutdown/restart and provider error. Define accepted, pending, delivered, cancelled, failed and uncertain states; give every input stable identity, source, content/attachments, mode and ordering. Decide if submit+interrupt is atomic and what happens to already accepted entries.
2. Extend the durable admission/receipt design rather than adding a second ephemeral authority. Serialize promotion with loop ownership; establish crash-safe persistence and exactly-once *admission* without promising exactly-once external tool effects. Define capacity/backpressure, FIFO within a mode, cross-mode precedence, clear/delete, replay, and session isolation. Use explicit rejection instead of silently dropping accepted work.
3. Add safe-boundary promotion in the shared streaming/tool orchestration path, including simultaneous tool calls: finish or explicitly cancel/settle all required tool results before placing new user content in provider-valid history. Check before subsequent provider request and before final completion to avoid stranded/racy steer. Test Codex native checkpoints, provider-specific ordering, retries, compaction and continuation, not just string history.
4. Wire user selection/status through TUI, CLI, session manager, embedded and remote RPC, bridge and any opt-in AgentManager/scheduler paths. Preserve existing behavior unless an intentional contract change is approved; return admission errors rather than silently reporting success. Expose pending/delivered state and cancellation/edit only if specified.
5. If polling is requested, define an explicit tool schema, empty response, FIFO/ack semantics, concurrent poll exclusion, durability, permissions and behavior when never called. It should coexist with deterministic turn-end handling rather than hold messages indefinitely. Differentiate it from HITL `request_user_input` and process `write_stdin`.
6. ACDD: create feature scenarios first, then failing integration tests with real stores and controllable streaming provider/tool boundaries. Cover each mode, overlapping inputs, in-flight generation and tools, interrupt races, failure/restore, session isolation, pressure, UI/RPC transports, compaction and native Codex history. Run targeted package/test binaries, never unscoped workspace tests.

## Decisions for discovery

- Is the intended queue explicitly **LLM-invoked polling**, automatic next-turn follow-up, or both? What is the forgotten third mode: steer, or interrupt-and-replace?
- Which keybindings/default mode and which front doors are in initial scope? Should existing AgentManager busy rejection remain default?
- On interrupt, should accepted pending messages remain parked, resume automatically, be cancelled, or be editable? Is replacement destructive only by explicit opt-in?
- What should happen when steering arrives while a tool is running or just as a turn finishes, and which attachment types are supported?
- What durability, acknowledgement/idempotency and queue capacity guarantees are required, especially across a crash or client retry? How should queue and steer interact with compaction, Done and uncertain dispatch?
