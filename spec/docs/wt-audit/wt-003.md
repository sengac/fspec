# WT-003 — Session worktree RPC ops resolve the repo via `std::env::current_dir()`

## Problem

Every session-worktree operation in the RPC handle layer resolves the repository path from the
**process's current working directory at call time**, not from the session's recorded project
root:

`rust/sessions/src/handle_impl.rs`:

| Method | line | repo_path source |
| --- | --- | --- |
| `merge_session_worktree` | 1942 | `std::env::current_dir()` |
| `discard_session_worktree` | 1971 | `std::env::current_dir()` |
| `prune_orphaned_worktrees` | 1978 | `std::env::current_dir()` |
| `list_session_worktrees` | 1995 | `std::env::current_dir()` |
| `inspect_session_changes` | 2035 | `std::env::current_dir()` |

The comment in the file (`rust/sessions/src/handle_impl.rs:1928`) states the rationale:
*"The repo_path is resolved at call time via std::env::current_dir(), matching the
blocklist_list pattern above."*

But worktrees are created under **`<project>/.fspec/worktrees/<session_id>`** where
`<project>` was captured at session-creation time
(`create_isolated_session_with_id(id, model, project, name)` — `session_manager.rs:916`;
`codelet_git::create_worktree(project, id)` at `:935`; manifest `worktree_path` at `:944`).
If the process cwd differs from the project root, all five operations aim at the wrong tree.

## Live verification (done 2026-09-06, scratch test since removed)

```text
# merge_session called with the repo root as argument — works:
Ok(MergeResult { session_id: "merge-subdir", files_added: ["from-session.txt"], .. })

# same call with a SUBDIRECTORY of the repo as argument (what current_dir() would be
# if the TUI was launched from, e.g., <repo>/rust):
Err(OpenRepository { path: "/tmp/.../rust", source: NotARepository { source: MissingHead } })

# with a completely foreign cwd:
Err(OpenRepository { path: "/tmp/...", source: NotARepository { source: MissingHead } })
```

`codelet_git::open_repo` uses `gix::open` (strict, no discovery —
`rust/git/src/lib.rs:57-63`), so a subdirectory of the repo is *not* treated as the repo;
`gix::discover` would have found it, but the worktree paths are still joined onto the
supplied path (`repo_path.join(FSPEC_WORKTREES_DIR)`, `worktree.rs:100`), so even
discovery would not fix the join.

## Why "launched from elsewhere" is realistic

- `fspec combined` / `fspec daemon` take the workspace as a resolved argument
  (`common::resolve_workspace`, `rust/fspec/src/common.rs`), but the process cwd is
  wherever the user started the binary.
- A user can start `fspec` in `~/projects`, then open a project in `~/projects/foo`
  (TUI workspace switching / resume from another project).
- The NAPI/TS frontend passes `currentProjectRef.current` explicitly (see the architecture
  docstring in `spec/features/merge-worktree-command.feature`), which is why the TS path
  does not hit this — the Rust handle layer simply dropped the parameter.

## Impact

- `/merge-worktree` (RPC-057) fails with `[error] /merge-worktree: … Not a repository`
  even though the session's worktree exists and has changes → user perceives
  "/merge-worktree doesn't work".
- Same for discard, inspect, list, prune — the entire worktree-management surface is
  cwd-sensitive.
- `prune_orphaned_worktrees` is doubly broken: the active-session set it passes is built
  from `self.list_sessions(current_dir_string)` (in-memory session list per project
  path string) — a cwd mismatch also skews the "which sessions are active" input.

## Proposed fix

1. Read the project root from the session's manifest / `BackgroundSession.project`
   (`session.project`, `rust/sessions/src/background_session.rs`) instead of
   `std::env::current_dir()`:
   - `merge_session_worktree` / `discard_session_worktree` /
     `inspect_session_changes` already have the `session_id` — look the session up and use
     its `project` (fall back to `manifest.project_root` from
     `codelet_git::read_manifest` for sessions not in memory).
2. `list_session_worktrees` / `prune_orphaned_worktrees` have no session id — either (a)
   enumerate across every in-memory session's distinct project roots (dedup), or (b)
   accept an explicit `project` parameter on the wire (schema change), or (c) keep the
   cwd fallback but log a warning when the resolved repo root ≠ any known session project.
   Recommend (a) with (c) as the guard.
3. Add a source-shape / integration test: create a session with project X while
   `current_dir()` is Y, then call `merge_session_worktree` → expect success.
4. Consider making `codelet_git::open_repo` fall back to `gix::discover` when
   `gix::open` fails with NotARepository — defensive, but the real fix is passing the
   right path.
