# WT-005 — Closing/destroying an isolated session leaks its worktree forever (no termination, no prune UI)

## Problem

There is no reachable path from the product UI to reclaim a session worktree whose session
was closed (rather than merged/discarded). The pieces exist in `codelet-git`, but the
production wiring that would make them work is missing:

### The intended lifecycle (GIT-022 / GIT-026, `rust/git/src/session_status.rs`)

- Manifest per session: `~/.fspec/git-sessions/<session-id>.json`
  (`SessionManifest { terminated: bool, … }`).
- `terminate_session(id)` → sets `terminated = true`.
- `is_orphaned(id, active)` → orphaned when **not** in `active_sessions` AND
  (manifest missing OR `terminated`).
- `prune_orphaned(repo, active)` → removes worktree + manifest for orphans.
- `complete_session(id)` → marks `completed_at`.

### What production actually does

1. **`terminate_session` has zero production call sites.** Grep across `rust/` shows only
   tests calling it (`session_orphan_pruning_tests.rs:110`,
   `session_status_tests.rs:332`). `SessionManager::destroy_session`
   (`rust/sessions/src/session_manager.rs:1243`) — the "Close session" path — cleans up
   in-memory state and tool registries but:
   - never calls `terminate_session`,
   - never calls `remove_worktree` / `discard_session`,
   - deliberately keeps the persistence manifest on disk (documented PARITY FIX at
     `:1283` — for `/resume` support).

   So after closing an isolated session: worktree dir exists, git-session manifest exists
   with `terminated: false` → `is_orphaned` returns **false** → `prune_orphaned` never
   reclaims it. It is, by the code's own definition, *not* orphaned — and no other state
   exists that would let it be found.

2. **`prune_orphaned` is exposed as RPC but has no frontend caller.**
   `prune_orphaned_worktrees` exists on the handle trait
   (`rust/core/src/session_manager_handle.rs:840,2285`), the tarpc service
   (`rust/rpc/src/lib.rs:623,2143`), and both TUI transports
   (`embedded.rs:933`, `websocket.rs:1271`) — but nothing in the TUI calls
   `backend.prune_orphaned_worktrees()` (no `/` command, no board view action, no dialog
   dispatch references it; `dispatch_merge_worktree.rs` covers only merge/discard/cancel).

3. **`prune_orphaned_worktrees` itself is cwd-sensitive** (see WT-003:
   `repo_path = std::env::current_dir()`, `handle_impl.rs:1978`) and its active-set input
   is `self.list_sessions(current_dir_string)` — in-memory sessions for the cwd project.
   So even a wired-up call would prune against the wrong repo.

4. **No listing UI.** `list_session_worktrees` (RPC-057 surface) exists but is likewise
   uncalled by any TUI view — there is no "session worktrees" panel where a user could
   discover a leaked `.fspec/worktrees/<uuid>/`.

## Impact

- Every `/isolation` → work → close-session cycle that does not end in
  `/merge-worktree` or the discard button leaks:
  - `<project>/.fspec/worktrees/<uuid>/` (a full checkout — for a repo like fspec, that's
    hundreds of MB),
  - `<project>/.git/worktrees/<uuid>/` metadata,
  - `~/.fspec/git-sessions/<uuid>.json`.
- The leaks are invisible: no status, no listing, no cleanup command.
- `derive_session_status`/`list_sessions` (GIT-023, NAPI `list_sessions`) would *eventually*
  surface these as `Clean` sessions of unknown provenance — but only via the NAPI export,
  which the Rust binary doesn't call.

## Proposed fix (options, in increasing scope)

1. **Terminate on close (minimal, correct semantics).** In `SessionManager::destroy_session`,
   when the session has a `worktree_path`, call
   `codelet_git::terminate_session(&id)` *unless* the worktree was already merged/discarded
   (guard: check `~/.fspec/git-sessions/<id>.json` still exists / worktree dir still
   exists). Keep the persistence manifest for `/resume` — only the git manifest gets
   `terminated: true`.
2. **Wire prune into the UI.** A `/worktrees` (or extend the board view with a
   "session worktrees" section) that calls `list_session_worktrees` +
   `prune_orphaned_worktrees` (fix repo-path per WT-003 first).
3. **Explicit per-worktree actions.** Reuse the `MergeConfirmDialog` from the listing so a
   leaked worktree can be merged/discarded later — this also fixes the "I closed the
   session but my work is in the worktree" data-loss scenario.
4. **Startup sweep (belt-and-braces).** At `build_service`, run a non-interactive
   `prune_orphaned` for the resolved workspace project, logging what was pruned.

Recommended: 1 + 3 (terminate-on-close makes 4 unnecessary; 3 covers the data-loss case).
