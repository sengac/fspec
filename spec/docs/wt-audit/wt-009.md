# WT-009 — UX contract breaks: `/isolation` is not a toggle and `/merge-worktree` never closes the session

## Problem

The Rust TUI's worktree UX diverges from the reference behavior pinned in
`spec/features/merge-worktree-command.feature` (status `@done` for the TS TUI, whose
architecture docstring documents the intended flow: *"On success: show merge summary,
then cleanupCurrentSessionHandler() + destroySession() + onExit()"*).

### (a) `/isolation` — "Toggle worktree isolation" is not a toggle

`rust/fspec-tui/src/views/agent/slash_commands.rs:145-148`:

```rust
SlashCommand {
    action: SlashCommandAction::Isolation,
    description: "Toggle worktree isolation",
},
```

`rust/fspec-tui/src/app/dispatch_slash_commands.rs:157-162`:

```rust
SlashCommandAction::Isolation => {
    // RPC-060: routed via try_dispatch_create_session_dialog in app/dispatch.rs.
    let _ = self.action_tx.send(Action::OpenCreateSessionDialog {
        preselect: Some(CreateSessionOption::Isolated),
    });
}
```

It only **opens the create-session dialog** preselecting "isolated" (RPC-060). There is:

- no toggle-off (detach the current session from its worktree),
- no "isolate the current session in place" action (isolation is all-or-nothing: a
  *new* session),
- no feedback when an isolated session already exists (the dialog opens again).

So the description promises behavior that does not exist.

### (b) Merge success does not close the session or return to the board

`rust/fspec-tui/src/app/dispatch_merge_worktree.rs:207-219` (the TS-parity path):

```rust
MergeStatus::Success => {
    ...
    let _ = action_tx.send(Action::EmitSessionNotice(
        session_id,
        format!("[merge] success{commit}"),
    ));
}
```

After the server-side `apply_session_changes` **removes the worktree**
(`session_result.rs:242`), the TUI:

- emits a one-line notice and stops — no `destroy_session`, no `onExit()`-equivalent
  (no switch to BoardView),
- leaves the session alive while its `worktree_path` points at a **deleted directory**:
  - BashTool cwd (per WT-004's fix it would pin a deleted path),
  - footer poller cwd,
  - isolation context / badge (badge still says ACTIVE on a vanished worktree),
- a follow-up `/merge-worktree` in the same session fails with "worktree not found"
  instead of saying "already merged".

Compare the TS reference (feature docstring, scenario "Successful merge closes session
and returns to board"): merge → summary → `destroySession` → board view.

### (c) Minor: the conflict context message names the session id, not the path

`dispatch_merge_worktree.rs:240-249` `build_conflict_context`:

```rust
let _ = writeln!(out, "Effective worktree: {}", session_id.value);
```

The LLM is told "Effective worktree: <uuid>" — a session id, not a worktree path it can
act on. (It should print the worktree path, which the backend already returns in
`IsolatedSessionInfo` / the isolation state.)

## Proposed fix

1. Redefine `/isolation` as a real toggle:
   - non-isolated session → current behavior (open the dialog preselecting Isolated);
   - isolated session → detach: keep the session, drop `worktree_path`/context, emit
     `IsolationStateChange(false, None)` (server-side RPC required:
     `detach_session_isolation(session_id)` — or rename the existing discard-to-session
     semantics). Update the description to match whatever lands.
2. On `MergeStatus::Success` in `handle_merge_confirmed`: send
   `backend.destroy_session(sid)` (or a new `close_session_after_merge`), switch
   `navigator.active_view` to Board (mirror the Board→Agent flip in
   `handle_create_session_submitted`, `dispatch_create_session_dialog.rs:71-73`), and
   guard re-merges with a "worktree already gone" notice.
3. Fix `build_conflict_context` to use the worktree path (obtain via
   `list_session_worktrees` or extend `MergeOutcome` to carry it).
4. Spec: add scenarios to a `@worktree-isolation`-tagged feature file covering (a)/(b),
   mirroring the TS feature file's scenarios.
