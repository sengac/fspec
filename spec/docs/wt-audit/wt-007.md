# WT-007 — `/resume` silently drops worktree isolation for formerly-isolated sessions

## Problem

Resuming a session never restores its isolation state. In
`SessionManager::create_session_from_manifest` (`rust/sessions/src/session_manager.rs:770`+),
the shared-creation params are hard-coded to the non-isolated shape:

```rust
let params = SessionCreationParams {
    ...
    worktree_path: None,
    base_commit: None,
    isolation: None,
    ...
};
```

(`session_manager.rs:848-850`)

Meanwhile `create_session_with_id` passes the same three fields explicitly as
`None` (`:655-657`), and only `create_isolated_session_with_id` populates them.

Two manifest schemas exist and **neither is consulted for isolation data**:

1. **Persistence manifest** (`rust/core/src/persistence/manifest.rs:106`,
   `~/.fspec/sessions/...`) — has `id, name, project, provider, messages, forked_from,
   merged_from, compaction, token_usage`. **No** `worktree_path` / `base_commit` fields.
2. **Git session manifest** (`rust/git/src/session_status.rs:54`,
   `~/.fspec/git-sessions/<id>.json`) — **does** store `worktree_path: Option<PathBuf>` and
   `base_commit: Option<String>` (written by `create_session_manifest` in
   `create_isolated_session_with_id`, `session_manager.rs:941-947`) — but
   `create_session_from_manifest` never calls `codelet_git::read_manifest`.

## Consequences after a restart (or closing and re-opening)

For a session that was isolated before the restart:

- `BackgroundSession.worktree_path` = `None` → `effective_cwd()` = project root
  → Bash runs in the main project, not the worktree (and with WT-004's fix applied,
  path isolation would block the worktree as "outside" — a regression vector).
- No `IsolationContext` is injected into the environment reminder
  (`inject_context_reminders` instead of `..._with_isolation`,
  `session_creation_helper.rs:216-220`) → the LLM believes it is in the main project.
- No `IsolationStateChange(true, …)` chunk is emitted (compare
  `create_session_with_id`'s explicit `isolation_state_change(false, None)` at
  `session_manager.rs:738-742` and the isolated path's `true` emission at `:1183`) →
  the TUI badge shows non-isolated.
- The worktree on disk is still there, untouched, unreachable: not in any session,
  not in the merge flow (the session id it belongs to has a fresh non-isolated session
  now), and — per WT-005 — not prunable because the git manifest says `terminated: false`.

Net effect: isolation is a **process-lifetime** property that cannot survive a restart,
and the durable artifacts it creates leak.

## Proposed fix

1. On resume (`create_session_from_manifest`), call
   `codelet_git::read_manifest(&uuid_string)`; if it exists, has a `worktree_path`, and
   that directory still exists (plus `repo.git_dir()/worktrees/<id>`), rehydrate:
   - `worktree_path` / `base_commit` into `SessionCreationParams`,
   - build the `IsolationContext` exactly like the isolated-create path does
     (relative path + short base),
   - emit `IsolationStateChange(true, …)` after insert (mirror `:1183`),
   - re-register the footer poller with the worktree cwd (mirror `:1191`).
2. If the worktree dir is gone but the manifest claims isolation, fall back to
   non-isolated + log a warning (and mark the git manifest terminated so prune can
   reclaim strays — links to WT-005).
3. Add a source-shape test (pattern of `session_manager_shape.rs`) asserting
   `create_session_from_manifest` references `codelet_git::read_manifest`.
4. Integration test: create isolated session in a temp repo → simulate restart (new
   manager) → `create_session_from_manifest` → assert `worktree_path` is Some and an
   `IsolationStateChange(true,…)` chunk was broadcast.
